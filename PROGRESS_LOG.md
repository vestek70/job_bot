# PROGRESS LOG — Job Bot

Бортовой журнал проекта. Каждая рабочая сессия (в том числе AI-агент в VS Code)
добавляет новую запись СВЕРХУ (последняя запись — самая свежая), не переписывая
старые. Формат записи:

```
## ГГГГ-ММ-ДД — Короткий заголовок изменения

### Что сделано
- ...

### Файлы изменены
- `path/to/file` — что именно поменялось

### Проверка
- Как проверено (запуск, тест, ручная проверка) и результат

### Дальше
- Что осталось / следующий шаг (опционально)
```

Не удалять старые записи и не переписывать историю — это журнал, а не резюме
изменений. Если нужно исправить что-то из прошлой записи — добавляется новая
запись с пометкой, что именно исправлено и почему.

  ушла — `.git` теперь пишется нормально. Сделан первый коммит (`git init` уже был,

  пустые). Поэтому реальный end-to-end (Adzuna → Anthropic) НЕ проверялся — по
  инструкции не подставлял фейковые ключи. Вместо этого закрыл P0-пункты backlog,
  которые тестируются без ключей.
- **P0: фильтр по сеньорности** — новый `filters.py` (`is_too_senior`,
  `filter_out_senior`): отсеивает вакансии выше pleno (по названию: senior/sênior/

- **P0: экспорт в PDF** — новый `export_pdf.py` (`markdown` + `xhtml2pdf`, чистый
  Python, работает на Windows без внешних бинарников, PDF с настоящим выделяемым
  текстом → читается ATS). Генерируется автоматически после каждого `resume.md`
  (флаг `EXPORT_PDF`), либо запускается отдельно (`python export_pdf.py [путь]`).
  Провал генерации PDF не роняет пайплайн — `.md` остаётся.
- **P0: обработка ошибок API** — Adzuna (`_get_with_retries`) и Anthropic
  (`tailor_one`) теперь ретраят транзиентные ошибки (429/5xx/timeout) с экспо-бэкоффом,
  дают понятное сообщение при неверных ключах (401/403) вместо traceback, и
  изолируют сбой по одной вакансии (пропускают её, не роняя весь прогон).
- **Побочно найден и починен реальный баг:** на Windows-консоли в не-UTF-8 локали
  (здесь cp1251) `print()` с португальскими акцентами падал с `UnicodeEncodeError` —
  уронил бы любой прогон у пользователя. `config.py` теперь реконфигурирует
  stdout/stderr в UTF-8 при импорте (его импортируют все entry points).
- **P1 (частично): юнит-тесты** — `test_filters.py` покрывает `is_too_senior`,
  `filter_out_senior`, `slugify` (6 тестов, все зелёные). Есть минимальный
  встроенный ранёр — работает и без pytest.

## 2026-07-22 — Попытка git init + разбор нужных MCP (сравнение с PLATFORMA 5)

### Что сделано
- По просьбе пользователя изучен `D:\PLATFORMA 5\.mcp.json` и `.kilo/kilo.jsonc` —
  реальный рабочий конфиг MCP-серверов другого проекта пользователя, чтобы понять,

- Вывод: из 9 серверов там (filesystem, sequential-thinking, brave-search,

  context7, gsc) для `job_bot` реально полезны только **github-mcp-server** (репозиторий
  vestek70/job_bot) и **context7** (доки библиотек). Остальные либо избыточны

  (gsc, floripa-portuguese, gcp/gmp-code-assist), либо пригодятся позже (supabase —

- Подготовлен `.mcp.json` с этими двумя серверами (по образцу рабочего конфига из
  PLATFORMA 5, с плейсхолдером `${GITHUB_PERSONAL_ACCESS_TOKEN}`, без реальных
  секретов).

  подключённый диск (сетевой mount) не поддерживает операции, которые нужны git

  недоинициализированная папка `.git` с зависшим `index.lock`, которую не получилось
  удалить с этой стороны (нет прав на mount). **Требуется ручное вмешательство
  пользователя** — удалить `.git` вручную и сделать `git init`/`push` из терминала
  VS Code на своём компьютере (там же безопаснее с точки зрения GitHub-токена).
- Искал GitHub-коннектор в реестре Cowork (`mcp-registry`) — не нашёлся в каталоге
  под этим именем, поэтому подключение к приватному репозиторию сделано через
  обычный git + `github-mcp-server` (Claude Code MCP), а не через встроенный
